What happens when one reading arrives

A sensor on a chiller reports a number. Thirteen stages later, a named person is asked to do a specific job on a specific machine, with a price on doing it and a price on waiting. This is every stage in between, in order, with the table each one writes.

Read this first

Today this is a batch pipeline, not a live streaming service. Readings are loaded, then each layer runs over what is stored. If you connected a live feed shaped like app.measurements, every stage below would still run, in this order, reading the same tables and writing the same rows.

Nothing here is one recursive call per datapoint. Each stage reads the latest stored measurements and derived tables and writes its own results. Advisories are assembled at the end. That is a real architectural difference and it is stated here rather than discovered later.

Eleven layers, each consuming the one above

Nothing skips a layer and nothing reaches back up. That constraint is why a wrong number can be traced to the stage that produced it, and why adding a new kind of machine does not require touching the prediction maths.

The numbering below is not decoration. Stage seven cannot run until stage six has written its rows, and the last four stages only run at all once the earlier ones have found something. Three of the stages exist mainly to refuse — and that is the point of the design, not a gap in it.

Every stage is labelled with the module it lives in and the path to it — Ingestion, Rule engine, Remaining life, Advisory generation and so on — so any question about a stage has exactly one place to go and look.

critical under 50 degraded 50–69 watch 70–84 healthy 85+

Four tiers, and healthy is slate rather than green. A red-amber-green scale has no ends for the roughly one man in twelve with red-green colour deficiency, so every badge in the product also carries a word and its own shape. Colour never carries a judgement on its own.

Before any reading arrives

Eight things are already in the database. Live data does not redefine them — it feeds new numbers into them. This is the part a new site has to be set up with, and almost all of it is configuration rather than code.

Assets, points and units
Which instruments exist, what SI unit each reports, its physical bounds, and whether the column is usable at all. Three of this building’s 107 measurements are defective at source and are flagged with a written reason.
app.assets · app.points
The building’s topology
What feeds what, as a graph: towers to chillers, chillers to the chilled water loop, the loop to the air handler’s coil, the coil to five occupied zones. Walked upstream to find causes and downstream to count who is affected.
Brick model · app.asset_edges
Failure modes
Six named ways this equipment wears out. Each carries the formula for its degradation number, the value at which it counts as failed, a written physical justification for that value, and the kilowatts one unit of it wastes.
app.failure_modes
Rules
Nine physics assertions — six from a published air-handler rule set, three chiller performance rules. Each is registered against a class of equipment, so the engine works out which machines it applies to by asking the graph.
analytics/rules/ registry
Physics constraints
Balances that must hold if the instruments are telling the truth — mixed air, coil energy, chiller energy. Stored as arithmetic expressions in the model, so adding one is a line of configuration and not a code change.
model/extensions.ttl
Baseline catalogue
Which healthy-behaviour models apply to which class of machine, and which readings drive each one. Five models across two equipment classes, every term taken from the equation the equipment obeys.

Intervention library
Sixteen jobs. Each carries hours, trades, parts, cost and a written basis for the estimate. Keyed on the fault and the fault class, which is why one symptom can resolve to two different jobs.

The healthy reference
Twenty-one days somebody declares the plant was working. Every baseline is fitted on it and every health score is measured against it. Without this the system has no definition of normal for this specific machine.

The thirteen stages

Every stage states the question it answers, what it reads, what it does, and where the answer lands. The badge on each says how often it would need to run in a live deployment.

01
Ingestion ingestion/ every few minutes

The reading lands

Is this number in the system, in the right unit, at the right time?

  • A reading arrives: chiller-1.cdw_leaving_temp = 32.4 °C at time T.
  • Units are converted on the way in — nothing downstream ever handles a Fahrenheit or a gallon per minute.
  • The unit is a property of the ingestion manifest, checked once, not a property of every query.
  • Row written. The hourly rollup behind it refreshes, which is what charts and long-window fits read.
writes app.measurements app.measurements_hourly

No advisory yet. One reading cannot produce a maintenance decision, and a system that let it would be a system that alarms on noise.

02
Quality scoring analytics/quality/ every few minutes

Can this reading be believed?

Is the instrument telling the truth right now?

  • Five checks, each scored 0–100. The composite is the worst of the five, never the average — so one failure cannot be diluted by four passes.
  • Timeliness — did it arrive on the cadence it promised?
  • Completeness — are samples missing around it?
  • Range — is the value physically possible for this instrument?
  • Plausibility — did it jump further than the physics allows?
  • Staleness — has it stopped moving while the machine is running?
  • Bad readings are kept and explained, never dropped. A dropped reading looks identical to one that was never taken.
  • When a fault persists it becomes an instrument advisory — a statement about a thermometer, never about a chiller.
writes measurements.quality_score measurements.quality_flags app.sensor_advisories

Below a score of 50, no rule may see the reading — not by convention, but because the only route to a measurement refuses. This is the layer that stops “chiller fault” being reported when the actual problem was a twenty-dollar sensor.

03
Rule engine · mode gating analytics/rules/mode.py every few minutes

What is the machine even doing?

Is this a moment in which anything can fairly be judged?

  • Air handler classified into one of five operating modes: heating, free cooling, mechanical cooling with or without the economizer, unoccupied.
  • Chiller running state needs status and real power and real flow — one machine here reports status 1 for every sample of the year.
  • Judgement held back for one hour after the building opens, after a chiller starts, and after any mode change. Neither machine is in thermal balance then.
  • A chiller below twenty tons of load is skipped entirely: every per-ton quantity is dominated by dividing through a small number.
writes nothing — this gates the stages below

A rule that is correct in one mode is wrong in another. “The damper is in the wrong position” means something during occupied cooling and nothing at all overnight.

04
Rule engine analytics/rules/ every few minutes

Is something wrong right now?

Does any physics assertion about this machine fail to hold?

  • Nine rules, dispatched onto machines by asking the graph which ones are of the class each rule was written for.
  • Derived, not fitted — from conservation of mass and energy across the mixing box and the coils. That is why they work on day one, before any healthy history exists.
  • Firings are grouped into unbroken stretches, and reported only after holding for a full hour.
  • A stretch breaks on an evaluated instant that did not fire — but not on the gaps where evaluation was suppressed. A fault does not stop existing because the unit changed mode.
produces rule findings — one per machine, per rule, per sustained stretch

Nine afternoons of the same saturated valve is one finding, not nine — the operator needs to know the valve has been saturating for two months. Counting the other way would make the false-alarm rate a function of how choppy the weather was.

05
Physics constraints analytics/rules/constraints.py every few minutes

Do the instruments agree with each other?

Is this set of readings physically consistent?

  • Mixed air should be the blend of the outdoor and return air feeding it.
  • Coil energy — the heat leaving the coil should match the heat the water carried away.
  • Chiller energy — energy in should account for energy out.
  • Each miss is stored raw and normalised: how unusual it is against the spread the same balance showed when the plant was healthy.
  • Declared as arithmetic in the model, so adding a balance is a line of configuration rather than a code change.
writes app.constraint_residuals

These are not the main degradation signal. Their real job arrives at stage 10: a set of relations that ought to hold is what makes it possible to ask whether one lying instrument could explain everything.

06
Baselines analytics/baselines/ every few minutes

Is it behaving like its own healthy past?

Given exactly what is being asked of this machine right now, is this the number it should be producing?

  • Each baseline — fitted once on the 21 healthy days — reads today’s operating conditions and predicts what a working machine would read.
  • Stored per reading: observed, expected, the residual between them, and how many standard deviations that gap is.
  • Why not a limit on the raw signal: this fan’s power spans 0 to 1,622 watts across one perfectly healthy run.
  • No fixed value works. None inside that band avoids firing on ordinary operation; none above it ever fires.
  • After normalising, the same healthy run drifts 0.824 W in 120 days — three hundredths of its own standard deviation.
writes app.residuals

Every baseline is written in the form of the equation the equipment obeys, not fitted by throwing curves at data. So the coefficients can be checked by a person — and the model cannot predict cooling when there is nothing to cool with, which matters most during the fault.

07
Failure modes analytics/health/modes.py every few minutes

How far has each named failure progressed?

For this specific way of failing, what is the one number that tracks it?

  • The formula is read from the database, not written in code. It may reference a raw reading, a residual, or both.
  • Gated to the only conditions where it means anything: the coil-leak indicator exists only while the valve is commanded shut.
  • Every indicator counts upward as things get worse, whatever the underlying physics does.
  • For our chiller, condenser fouling is the stage 6 residual — how much hotter the leaving water is than a clean machine would leave it, at matched load and matched incoming water.
produces an indicator time series per machine, per failure mode

A new way of failing is one database row — a formula, a threshold, and a written justification for that threshold. No code at all. The justification column cannot be left empty, so a threshold can never enter without an argument recorded beside it.

08
Health index analytics/health/ once a day

Health, and whether decline has genuinely begun

How much of the way to failure has this machine travelled, and did it really start?

  • The day’s values reduce to one median. Degradation does not move on a five-minute timescale.
  • Onset first — a cumulative-sum test declares a start date when accumulated deviation from the healthy mean crosses its decision interval.
  • Then centre on what the machine read when it was healthy: excess over normal, not an absolute level.
  • Then clamp so the line can flatten but never climb. Equipment does not heal itself unless somebody repairs it.
  • Then map to 0–100: health = 100 × (1 − excess ÷ threshold).
  • A machine’s health is the minimum across its failure modes, never the average — and it records which mode produced it.
  • A recorded repair resets the clamp, so a cleaned condenser is not held at its worst-ever score forever.
writes app.health_state indicator_raw indicator_monotonic t_onset

Onset must run before the clamp: a clamped series is one-directional by construction, so a detector run afterwards would be finding the clamp rather than the fault. Both the raw and the clamped number are stored, so the clamp can be audited rather than trusted.

09
Remaining life analytics/rul/ once a day

How long has it got — or a refusal

If it keeps worsening like this, when does it reach the threshold that has a physical argument behind it?

  • The indicator is modelled as trend plus noise drifting toward its threshold. The distribution of when it first touches has a closed form — an expression, not a simulation.
  • Out comes a range, never a date: pessimistic, middle, optimistic. Nobody schedules a crew against a point estimate with no width on it.
  • The range tightens as evidence arrives. On the clearest case here it closes from 2,259 days to 59 across 84 daily estimates, as evidence goes from 14 samples to 53.
  • It also widens on the way, and says so — a run of flatter days genuinely is weaker evidence about a rate.
  • And it can refuse. Nothing publishes without: confirmed onset, 21 days of post-onset evidence, a rate of decline measurably above zero, and a range no wider than the observation behind it.
  • When it refuses, the reason is printed where the date would have gone.
writes app.rul_estimates … or the refusal, with its reason

Without this gate the raw maths reported that an air handler had already failed, on a rate half a standard deviation from zero, and gave a working chiller a failure date 254 days out. Across both fault-free runs — 720 combinations of machine, mode and day — it now publishes nothing at all. A remaining-life figure extrapolated from noise is worse than no figure, because it looks like an answer.

10
Diagnosis · isolation analytics/diagnosis/isolation.py once a day

Broken sensor, or broken machine?

Do we send somebody with a calibration kit, or somebody with a wrench?

  • Air leaving too warm is a coil that cannot cool and a thermometer reading high. From the symptom alone the two are identical.
  • Collect every relation that has stopped holding — the stage 5 balances and the stage 6 baselines, because a baseline is a relation too.
  • Ask: would one reading wrong by a consistent amount make all of them hold again?
  • Crucially: does the correction that fixes one relation break another the same reading appears in?
  • One bias reconciles everything → the instrument is the suspect. None can → the measurements agree with each other, so the machine is what changed.
produces a fault class per machine per window — sensor, equipment, control, or ambiguous

On a real drifting thermometer this recovered a bias of +2.434 K against a true injected +2.22 K, with no access to the answer key. Its power is a direct function of how many relations touch the suspect: a reading in only one relation is one equation in one unknown, and unfalsifiable by construction. So it improves by declaring another relation, not by tuning anything.

11
Diagnosis · root cause analytics/diagnosis/rootcause.py once a day

Is this machine the patient, or showing someone else’s fever?

Could an open fault upstream be producing this symptom?

  • Walk the graph upstream and find open faults on machines that feed this one.
  • Topology alone is not grounds for a link. Two connected machines with faults at the same time are usually a coincidence.
  • A cause must degrade the medium this machine consumes — a declared table of mechanisms, not an opinion about which faults feel related.
  • When the mechanism applies: mark consequential, link it to the cause, and demote it below — so fixing the cause makes the symptom disappear on its own.
  • Never hidden.
produces a consequential link and a demoted rank, carried into the advisory

Demoting wrongly gives a badly ordered queue and the operator works the row anyway. Suppressing wrongly makes a real fault absent, and they find out when the equipment fails. The queue may be badly ordered; it must never be incomplete.

12
Advisory generation analytics/advisories/ once a day

The advisory — the only thing a human acts on

What should be done, by whom, and what does waiting cost?

  • What — the machine, the failure mode or rule, the fault class, the health score.
  • When — the three dates, or the refusal and its reason.
  • Why — every contributing signal with its actual measured value, its healthy reference, and how far it has moved. Plus how many readings were excluded, and whether the quality layer condemned them or the source column never meant what its name said.
  • Who is affected — the zones downstream and the occupants in them, read off the model rather than typed in.
  • Severity — the two things the system measured carry 0.7 between them; the two that are business context carry 0.3. Context should shade a ranking, not decide it.
  • Cost of waiting, over 90 days, because that is a budget period. Energy: indicator × kW-per-unit measured on a healthy run × running hours × tariff. Plus: chance of crossing inside the horizon × (replacement − repair).
  • Cost of acting — the matching job from the library: hours at the site labour rate, plus parts.
  • Priority — expected dollars saved per dollar spent.
writes app.advisories

When neither cost term can be computed the row is marked unpriced — never 0.00. Zero is a claim: it says the fault is free to ignore, and a saturated cooling valve serving two hundred people is not. The queue is two tiers: priced rows ranked on money, unpriced rows after them on severity.

13
API and interface api/ · web/ on request

The screen

What does the operator see, and can they trust it is only what was known at the time?

  • Nineteen read-only endpoints over the stored tables.
  • The interface computes no physics. Formatting, charting and layout live in pure modules, which is why the display logic is verified in a terminal without a browser.
  • Every screen reads one shared clock, and every endpoint it drives truncates strictly.
  • At any chosen moment, nothing computed after that moment is visible anywhere.
writes nothing — every endpoint reads

That single rule is what makes a replay of stored results indistinguishable from a live system — the range narrows while you watch, an advisory appears rather than having always been there — without any of it being staged.

One reading, all the way down

The same number, traced through every stage. The point chosen is real: the temperature of the water leaving chiller 1’s condenser, which is the target of a baseline and the indicator for a failure mode, so it exercises the whole chain.

Coefficients, thresholds and costs are configuration read from the database and the semantic model. Duty and probability are measured per window at run time.

02  Quality Scored on five checks; the composite is the worst of them. Must clear 50 to be used as evidence anywhere. quality_score, quality_flags
03  Context Is chiller 1 actually running — status and power and flow? Started more than an hour ago? Above twenty tons? — gate only
04  Rules Read by two of the three chiller rules as an input. A firing must hold for an hour before it is reported. rule findings
05  Constraints Appears in chiller 1’s energy balance. Miss recorded raw and normalised. app.constraint_residuals
06  Baseline It is the target of the condenser heat-rejection model, driven by chilled water in, out, flow, and entering condenser water. Expected value predicted; observed − expected stored. app.residuals
07  Indicator That residual is the condenser-fouling indicator. Failure threshold 3.0 K of excess — roughly a 7–9% compressor power penalty, the point a tube brushing pays for itself in one season, and seven times the fitted baseline’s own spread, so it cannot be reached by scatter. indicator series
08  Health Daily median, onset test, centre, clamp. At 1.5 K of excess: 100 × (1 − 1.5 ÷ 3.0) = 50. Health 50 is degraded. app.health_state
09  Prediction Modelled as accumulation only — scale and biofilm settle on tubes and stay there until somebody brushes them out, so a process that forbids the indicator going backwards is the physically correct one. Three dates, or a refusal. app.rul_estimates
10  Diagnosis Chiller 1 offers three relations and its power meter appears in two of them — so a developed fault here can be misread as a faulty meter. This is a known and documented weakness, fixed by declaring more chiller relations. fault class
11  Root cause Chiller 1 is fed by a cooling tower. If the tower had an open fault that warms condenser water, this advisory would be marked consequential and demoted beneath it. consequential link
12  Advisory Energy: excess K × 1.876 kW/K (2.5% of this machine’s measured mean 75.04 kW compressor power, per kelvin of extra lift) × running hours × $0.128/kWh. Consequential: chance of crossing within 90 days × ($165,000 − $18,000). Against acting: brush the condenser tubes — 8.0 h at $95/h plus $850 of consumables = $1,610. app.advisories

Every number in that last row is traceable. The kilowatts-per-kelvin coefficient carries its own arithmetic in the database next to it, including the honest note that the 2.5% figure is a handbook rule of thumb while the 75.04 kW it multiplies is measured on this machine. The tariff and the labour rate are read from the semantic model and the code refuses to default them — a cost of inaction computed against a made-up tariff is exactly the kind of number this project will not produce.

What actually touches one reading

Not every stage cares about every point. Here is the honest answer for a single new sample — and the reason one datapoint rarely creates an advisory on its own.

Stage Uses this point? Immediate output
Quality always A score and any failing checks; an instrument advisory if it stays bad
Rules if a rule reads it A sustained finding, or nothing
Constraints if it is in a balance One residual row
Baselines if modelled, or a driver One residual row
Failure-mode indicator if a mode references it One indicator sample
Health & onset only in aggregate Nothing today — contributes to the daily median
Prediction only after onset Nothing until onset is confirmed and 21 days of evidence exist
Diagnosis if its relations are violated A sensor-versus-equipment verdict
Root cause if this machine has an open fault Possibly a consequential link and a demotion
Advisory needs an open fault A ranked, costed job — only once accumulated evidence exists

One bad sample does not become “replace the chiller tomorrow.” An advisory appears when an open fault exists with enough accumulated evidence behind it — which is the difference between a maintenance tool and an alarm panel.

If you ran this live

The stages split cleanly into two loops, and the split is already how the code is structured — because degradation does not move on a five-minute timescale and pretending it does would only add noise.

Fast path

every few minutes
ingest→ quality→ context→ rules→ constraints→ baselines→ indicators

Everything that is a statement about right now. Runs on a recent window, so cost scales with the window rather than with history. This is the loop that catches an instrument going bad and a rule being violated.

Slow path

once a day
health & onset→ prediction→ diagnosis→ root cause→ advisories

Everything that is a statement about a trend. Health is defined per day by design. Advisories are rewritten when the open-fault picture changes, so the queue an operator opens in the morning is a coherent snapshot rather than a shifting list.

What gets harder in a genuinely streaming deployment is not the protocol — a new source sits behind the existing manifest interface, and nothing downstream knows where a reading came from. It is the semantics: readings that arrive late or out of order, gaps that are network outages rather than dead sensors, and the fact that the hourly rollup and the daily health computation both currently assume a complete window.

Four things that never happen

Each of these is a decision rather than an omission, and each one makes the system look less complete and more trustworthy.

The detection path never reads the answers
Every layer that detects, scores, baselines, predicts or diagnoses connects to the database as a role with no grant of any kind on the schema holding the labels — not restricted access, none. A query from that side fails with permission denied. Exactly two components hold the other credential and neither computes anything: the accuracy harness, and the one screen that shows the answers. They run as separate processes, so the separation does not rest on nobody adding the wrong import.
Nothing is written back to a machine
There is no write path to any actuator, ever. Adjusting setpoints on the strength of an inference that can be wrong is a different product with a different safety case. This one advises a human, and sits beside a building automation system rather than becoming one.
The interface never computes a prediction
Every screen reads stored rows. If a number is wrong it is wrong in one place, and it is the same number a script can print in a terminal. No chart is allowed to disagree with the ranking the analytics layer produced — the queue view deliberately does not re-sort.
A threshold is never moved to make a number look better
Every failure threshold carries a written physical justification in a column that cannot be left empty, precisely so that changing one requires changing the argument for it rather than only the value. If a result is bad, the fix is upstream of the threshold.

The whole thing in one paragraph

If you have thirty seconds

Readings land, get quality-scored, and then feed three things in parallel: physics rules, physics consistency checks, and models of what this machine does when it is healthy given what is being asked of it. Named failure modes read those residuals and turn them into one number each, rolled to a daily health score with a confirmed start date — and only then, optionally, projected into a range of failure dates, with an explicit refusal when the evidence will not carry one. Alongside that, we separate a lying instrument from a failing machine by asking whether one biased reading could reconcile everything, and we demote a symptom beneath an upstream cause when the mechanism actually permits it. The advisory assembles all of it: the diagnosis, the prediction or the refusal, who is affected, and what waiting costs against what acting costs.
